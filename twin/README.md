# Двойник завода: линия серы

Стационарная модель участка «сера → сжигание → конверсия → абсорбция»,
которая считает материальный баланс и позволяет менять управления.

## Как добавлять модуль

Модули `twin/*.js` работают в двух средах: в Node (проверки `node twin/*.selftest.js`)
и в браузере (вкладка «Двойник» подключает их тегами `<script>`). Классические
`<script>` делят **одну глобальную область**, поэтому:

```js
'use strict';
(function () {                    // ← обязательно
  // ...
  const API = { solve, designPoint };
  if (typeof module !== 'undefined' && module.exports) module.exports = API;
  else self.TwinModel = API;      // имя наружу — только так
})();
```

Внутренние имена (`solve`, `round`, `expandTag`) в браузере не видны — берите их
из соседнего модуля:

```js
const solve = (typeof module !== 'undefined' && module.exports)
  ? require('./model.js').solve
  : self.TwinModel.solve;
```

Это уже случалось дважды: страница падала с `Identifier 'API' has already been
declared`, при том что в Node всё проходило. Теперь проверяется автоматически —
`tools/ci-check.js`, проверка `scope`:

1. одно и то же имя на верхнем уровне в двух подключаемых файлах;
2. модуль с `module.exports`, подключённый тегом и не обёрнутый в IIFE.

Проверка входит в обязательный `checks`, поэтому забыть не получится.

## Блокировки (шаги 1–3)

**Разбор условий.** В исходнике 42 записи с 56 разными формулировками: «< 500 мм»,
«2 из 3 выше 150 мм», «остановлена», «> ** МПа» (уставка закрыта). Генератор
раскладывает их на поля: тип (аналоговое/качественное), оператор, значение,
единица, голосование «2 из 3». Где уставка в исходнике закрыта звёздочкой —
ставится `setpointUnknown`, а не выдуманное число.

Распределение после разбора: 58 аналоговых условий (26 с закрытой уставкой),
38 качественных.

**Сигналы.** `state.js` собирает состояние из результата модели (насосы кислоты и
воздуходувка работают, пока идёт выработка) и позволяет подмешать ручные значения.
Функция `coverage()` показывает, чего не хватает: сейчас блокировкам нужно
**87 тегов, у 83 из них сигнала нет** — это уровни, давления пара, температуры
масла. Такие блокировки получают статус `unknown`, а не «в норме».

**Логика.** `logic.js` умеет:

- аналоговые условия с операторами `<`, `<=`, `>`, `>=`, `=` и точкой входа «упало до»;
- качественные условия («остановлена», «в норме», «закрыт») — с учётом смысла слова;
- связки `or` (33 записи), `and` (2), `2oo3` (7); если «2 из 3» зашито внутри
  условия при одной причине-группе, связка не мешает;
- латч: 32 записи держатся до `RESET`, 10 — самовозврат;
- `BYPASS` отключает запись целиком.

Проверки: `node twin/interlocks.selftest.js` — 15 случаев, включая голосование
2 из 3, удержание латча, сброс, BYPASS и отсутствие сигнала.

## Тепловой блок

Пар считается из энергии реакций, а не «по коэффициенту»:

```
горение серы   S(ж) + O₂ → SO₂(г)     ΔH ≈ −297 кДж/моль S
конверсия      SO₂ + ½O₂ → SO₃        ΔH ≈ −99 кДж/моль SO₂
```

Тепло реакций идёт на испарение питательной воды (135 °C → пар 6,4 МПа / 450 °C,
Δh ≈ 2730 кДж/кг). Единственная подогнанная величина — КПД котла-утилизатора:
он подобран так, чтобы на номинале получилось **85,1 т/ч** пара по листу 2.
Вышло 0,926 — правдоподобно для котла-утилизатора.

Сходимость с балансом (лист 2):

| Параметр | Модель | Баланс |
|---|---|---|
| Пар 6,4 МПа / 450 °C | 85,13 т/ч | 85,1 (поток 111) |
| Питательная вода | 87,68 т/ч | 87,75 (поток 103) |
| Продувка | 2,55 т/ч | 2,63 (поток 112) |
| Тепло реакций | 69,8 МВт | — (расчёт) |

Мощность турбины считается **с отбором пара**: генерируемый пар 6,4 МПа идёт в
турбину, 16 т/ч отбирается при 0,8 МПа на плавление серы, обогрев и деаэратор,
остальное конденсируется. Каждый поток считается отдельно: отбор дорабатывает
только до 0,8 МПа, конденсационный поток — до конденсатора.

Отсюда мощность **20 МВт** при 85,1 т/ч пара. КПД турбины (0,85) подобран по
проектным данным (81,8 т/ч, отбор 16 т/ч, 19,1 МВт), а не придуман. Раньше в
модели было 8,3 МВт — потому что весь пар считался дорабатывающим до конденсатора,
что для схемы с отбором неверно.

Проверки: `node twin/heat.selftest.js` — 15 случаев, включая поведение при
остановке горения, на 70 % нагрузки и при отборе больше выработки пара.

## Температуры газа

Считаются из тепла реакций и энтальпии газа (табличные cp для N₂, O₂, SO₂, SO₃,
H₂O в диапазоне 300…1500 K, интегрирование трапециями).

Что считается физикой:

- **печь** — адиабатическая температура по теплу горения и подогреву воздуха
  (125 °C) и серы (135 °C), без единого подгоночного коэффициента;
- **ступени конвертера** — нагрев от тепла конверсии, делённого на теплоёмкость
  газа при текущей температуре.

Что задаётся уставкой (так и работает АСУТП): температуры на входе ступеней
(410 / 445 / 435 / 311 °C) и перед первой абсорбцией (275 °C).

Сходимость с проектом:

| Точка | Расчёт | Проект | Откл. |
|---|---|---|---|
| Печь, выход | 1 096 °C | 1 080 | +1,5 % |
| 1-я ступень | 615 °C | 608 | +1,2 % |
| 2-я ступень | 521 °C | 518 | +0,6 % |
| 3-я ступень | 458 °C | 457 | +0,2 % |
| 4-я ступень | 332 °C | 415 | −20 % ⚠ |

**Про 4-ю ступень.** Расхождение не в модели, а в проектном балансе: чтобы газ
нагрелся с 311 до 415 °C, нужно ~104 K, а тепло конверсии 30,9 кмоль SO₂ в газе
объёмом около 4 900 кмоль даёт лишь ~19 K. Точка помечена в интерфейсе как
«расхождение в балансе» — это стоит уточнить у проектировщиков.

Проверки: `node twin/temps.selftest.js` — 11 случаев, включая независимость
адиабатической температуры от нагрузки (тепло и теплоёмкость масштабируются
одинаково — это физика, а не совпадение).

## Плавление серы и уровни

Модель расширена вверх: от склада серы, а не от горелки.

`melt.js` считает тепло плавления из физики, а не по нормативу:

| Статья | На 20,48 т/ч |
|---|---|
| нагрев твёрдой серы 36 → 115 °C | 317 кВт |
| плавление (ΔH = 53,7 кДж/кг) | 306 кВт |
| перегрев расплава 115 → 145 °C | 171 кВт |
| **итого** | **793 кВт** |

Это даёт **1,39 т/ч** пара 0,8 МПа — сходится с ручной оценкой по проектным
данным (16 т/ч на плавление + обогрев + деаэратор).

Зольность считается балансом: вход (120 ppm) → кек + фильтрат, после первой
ступени ≤30 ppm, после второй ≤15 ppm. При нагрузке 46 % от проектных 45 т/ч
это выполняется; при 50 т/ч загорается предупреждение о превышении.

`tank.js` — первая динамика: уровень меняется по приходу минус расход.
Уставки взяты из таблицы DCS (`LT-11101`: LL 500, H 2200 мм), а не придуманы.

Цепочка, проверенная в браузере:

```
подача твёрдой серы 20,48 т/ч, расход на горелку 20,48 → уровень стоит
снизили подачу до 10 т/ч → за 6 часов уровень 1500 → 0 мм
→ сработала блокировка I-101 «Сухой ход насосов фильтрации 1-й ступени»
   по уставке LT-11101 LL = 500 мм (из DCS)
```

То есть сигнал, который раньше был «без сигнала», теперь **считается моделью**.

## Замкнутый контур: уровень → клапан → горелка

Расход серы на горение больше не задаётся отдельным ползунком — он берётся из
положения клапана (100 % = 45 т/ч, проектная производительность плавления).
Нагрузка завода считается как `расход / 20,48`, остальное масштабируется само.

Есть два режима:

- **ручной** — клапан двигает оператор, уровень уходит туда, куда ведёт баланс;
- **автомат уровня** — П-регулятор держит задание (по умолчанию 1500 мм),
  подправляя клапан на 2 % на каждые 100 мм ошибки.

Проверено в браузере:

```
старт: клапан 45,5 % → 20,48 т/ч → кислота 63,5 т/ч, уровень 1505 мм
3 часа в автомате → уровень 1505 мм, клапан не двигался (держится)
клапан вручную 20 % → 9 т/ч → кислота 27,9 т/ч
8 часов при 20 % → уровень 1505 → 11 755 мм (приток 20,48 против 9 т/ч)
```

То есть «прикрыть клапан на горелку» теперь значит: меньше кислоты, уровень
растёт, и через уставку H = 2200 мм сработает блокировка.

## Уровни по аппаратам

`vessels.js` держит 18 аппаратов с уровнем. Уставки — из таблицы DCS, площади
чанов — параметр модели (в документах их нет).

| Категория | Что значит | Сколько |
|---|---|---|
| `calc` | уровень считается моделью: приход расплава минус расход на горелку | 4 чана фильтрации |
| `manual` | прибор и уставки есть, модели потоков нет — уровень задаёт оператор | 14 |
| `none` | прибора нет вообще (маслобак, конденсатосборник) | 4 причины блокировок |

Уровневых причин в блокировках 23; значениями закрыто **18**. Остальные 4 —
масло и вода турбинного отделения (115), там приборов в таблице нет.

Панель «Уровни аппаратов» показывает уровень, уставку и статус; строка
`manual` выбирается и уровень ставится ползунком. Проверено в браузере:
установка `LT-13101` = 300 мм даёт срабатывание `I-13101` по уставке LL 500 мм.

## Уставки и диапазоны из таблицы DCS

Источник — `3147-5N100-03 «Таблица мониторинга данных DCS»` (17 листов по
отделениям). Сам xlsx в репозитории не хранится (3 МБ и права проектировщика);
из него собирается `twin/dcs-signals.data.js` генератором:

```powershell
python tools/gen-dcs-signals.py "D:\AI\Project\3147-5N100-03-*.xlsx"
```

Что получилось: **442 прибора**, у **425** есть диапазон измерения, у **91** —
уставки сигнализации `HH / H / L / LL`.

Сопоставление с блокировками (`twin/signals.js`) идёт по типу прибора и номеру
позиции: в схемах теги логические (`LIAS-11101`, `TE-PP11301`), в таблице —
полевые (`LT-11101`, `TE-11301`). Правило: `LIAS/LIA/LS → LT`,
`TIAS/TIA/TI/TE → TE`, `PIAS/PIS/PI/PT → PT`, `FIAS/FIA/FI/FT → FT`.

Результат: **35 условий из 96** привязываются к прибору, у **24** из них есть
уставка.

**Перекрёстная проверка.** Схема `I-101` требует «уровень < 500 мм», а в таблице
DCS у `LT-11101` стоит `LL = 500 мм`. Два независимых документа дали одно и то же
число — это лучший признак, что и схемы, и таблица прочитаны верно.

**Чего таблица не даёт.** Закрытые в схемах уставки (`> ** °C`, `≥ ※ мм` —
26 условий) относятся к защитам (ПАЗ): приборов `VT-` (вибрация), `TIAS-11350…`,
`PIAS-11367` в таблице мониторинга нет вообще. Это отдельный комплект уставок
САУ/ПАЗ, его нужно запрашивать отдельно. Проверка в `selftest` фиксирует это
явно, чтобы не создавалось впечатление, будто пробел закрыт.

## Связь блокировок с расчётом (шаг 4)

`apply.js` переводит следствия в ограничения модели — только там, где физика
очевидна:

| Следствие | Что в модели |
|---|---|
| останов `BO-11301` / `YSS-BO-11301` | горение прекращено: кислота 0, выброс 0 |
| останов `PP-11302` | орошение 1-й абсорбции снято (`absorb1 = 0`) |
| останов `PP-11303` | орошение 2-й абсорбции снято (`absorb2 = 0`) → SO₃ уносится в трубу |
| останов `PP-11301` | не смоделировано (сушка газа) — помечается честно |

Цепочка, которая видна на вкладке: останов насоса 2-й абсорбции → `B-PROC`
(«остановлен») → аварийный останов воздуходувки → горение прекращено. Латч
держит останов и после возврата насоса — пока не нажат сброс, как на щите.

## Как считается

1. Из расхода серы — количество SO₂ и SO₃ (доля SO₃ задаётся, проектная 2,65 %).
2. Воздух задаётся расходом кислорода; азот — по проектному отношению из баланса.
3. Четыре ступени конверсии: доля превращения SO₂ задаётся по каждой ступени
   (проектные 64,0 / 65,7 / 58,3 / 97,0 %). Между третьей и четвёртой — первая
   абсорбция, она убирает SO₃ из газа.
4. Кислота — из уловленного SO₃: 1 кмоль SO₃ даёт 1 кмоль H₂SO₄.
5. Труба — остаток SO₂ после щелочной промывки, пересчёт в мг/нм³ по влажному объёму.

## Чего пока нет

- **Температуры газа** считаются, но входы ступеней заданы уставками: тепловой
  расчёт не подбирает их сам, а проверяет, какой нагрев даёт тепло конверсии.
  Часть таблицы листа 2 закрыта штампом — потоки 116 и далее прочитаны не полностью.
- **Динамика.** Модель стационарная: «было — стало», без переходных процессов.
- **Мощность турбины** — оценка по допущению КПД, а не расчёт.
- **Сигналов не хватает.** 40 записей блокировок из 42 показывают «без сигнала»:
  нет уровней, давлений пара и температур масла.
