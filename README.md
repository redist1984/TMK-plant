# Завод TMK — офлайн-справочник сернокислотного завода

Браузерное приложение (PWA), которое собирает в одно целое 3D-модель завода,
технологическую схему, PFD, блокировки, анализы, перечень КИП и проектную
документацию. Работает без интернета — на планшете или ноутбуке в цеху.

**Живая версия:** https://redist1984.github.io/TMK-plant/

Объект — сернокислотный завод ООО «TMK Chemicals», 500 000 т/год, проект 3147.
Интерфейс двуязычный (RU / UZ), тема светлая/тёмная/системная.

## Разделы

| Вкладка | Файл | Что внутри |
|---|---|---|
| 3D-модель | `model.html` | 221 единица оборудования в 13 отделениях, трассы труб, карточки, галереи чертежей |
| Схема потоков | `flow.html` | потоки с параметрами, переходы в 3D и PFD |
| PFD | `pfd.html` + `pfd/` | 3 листа, 78 потоков с теплофизикой, 30 карточек оборудования |
| Блокировки | `interlocks.html` | 42 блокировки по 10 листам логических схем |
| Анализы | `analyses.html` | 25 точек аналитического контроля по регламенту п. 9.3 |
| КИП | `kip.html` | 384 прибора |
| Документы | `docs.html` | 151 PDF (планы, паспорта, ГА, ППР) |
| Настройки | `settings.html` | язык, тема, производительность |
| Помощь | `help.html` | справка по приложению |

## Структура

```
index.html            оболочка: шапка, вкладки, iframe-ы, шина postMessage
model.html            ровно одна страница на вкладку; данные зашиты внутрь
flow.html
pfd.html              + pfd/pfd-data.js, pfd/symbols.js, pfd/scan/*.jpg
interlocks.html       + interlocks-data.js, ilk-card.js
analyses.html         + analyses-data.js, anl-card.js
kip.html              + kip-data.js
docs.html             индекс PDF: путь -> заголовок (RU/UZ)
analyses-data.js      данные: приборы, анализы и т. п.
interlocks-data.js
kip-data.js
eq-uz.js              переводы описаний оборудования на узбекский
lang.js  theme.js     язык и тема; родитель рассылает их в iframe-ы
service-worker.js     precache + network-first (кэш только для офлайна)
manifest.json         PWA
vendor/               three.js и OrbitControls (локально, без CDN)
sec_img/              фото и сканы чертежей (178 файлов)
docs_pdf/             проектная документация (151 PDF)
tools/                генератор PFD, чекер CI, сборка офлайн-версии
```

Страницы — не модули, а самостоятельные документы: каждая грузится в свой
`iframe`, а оболочка `index.html` передаёт между ними сообщения
(`__tmkLangChange`, `__tmkThemeChange`, `__tmkGoto`, `__tmkFullscreen`).
Поэтому `model.html` и `flow.html` тяжёлые — в них зашиты и геометрия, и данные.

## Локальный запуск

Любой статический сервер из корня проекта (через `file://` не работает —
не зарегистрируется service worker):

```powershell
python -m http.server 8765
# затем http://localhost:8765/
```

## Проверки

```powershell
node tools/ci-check.js
```

Без зависимостей. Проверяет синтаксис всех `.js` и inline-скриптов, наличие
каждого файла из `ASSETS` в `service-worker.js`, полноту precache (все
подключённые страницами скрипты должны быть в нём), соответствие `docs.html`
↔ `docs_pdf/`, все `src`/`href` во всех HTML и ссылки галерей `IMGS` на
`sec_img/`.

Те же проверки гоняются в CI на каждый pull request
(`.github/workflows/checks.yml`).

**При изменении любого файла, перечисленного в `ASSETS`, поднимите версию
`CACHE` в `service-worker.js`** (`tmk-plant-v141` → `v142`): стратегия
network-first, но старый кэш иначе останется у тех, кто уже открывал
приложение.

## Офлайн-сборка одним файлом

```powershell
python tools/build_offline.py                  # dist-offline/TMK-plant-offline.html
python tools/build_offline.py --with-pdf       # + все PDF внутри (~230 МБ)
```

Скрипт вкладывает страницы в `index.html` как `srcdoc`-iframe, встраивает
скрипты и шрифты, картинки кладёт base64-блоками и отдаёт blob-URL по
требованию, service worker и manifest убирает. Результат открывается прямо
с диска по `file://`, без сети и без сервера.

## Android-приложение

`android/` — проект Android Studio: WebView-обёртка вокруг того же сайта.
Подробности в [android/README.md](android/README.md).

Главное: **контент в Android-проекте не хранится**. Каталог
`android/app/src/main/assets/www/` собирается из корня репозитория скриптом
`tools/build-android-assets.py` при каждой сборке APK и добавлен в
`android/.gitignore`. Поэтому правка любого файла в корне автоматически
попадает и в APK — второй копии, которая могла бы разъехаться с сайтом,
просто нет.

Приложение работает полностью офлайн: разрешение `INTERNET` не запрашивается,
внутри APK лежат все страницы, фото и PDF.

## Как это собирается

Три формы проекта собираются из одних и тех же файлов в корне:

| Что | Чем | Когда |
|---|---|---|
| Сайт | `pages.yml` — деплой корня на Pages | пуш в `main` |
| Офлайн-файл | `dist.yml`, job `offline` — `tools/build_offline.py` | PR, `main`, тег `v*` |
| APK | `dist.yml`, job `apk` — `tools/build-android-assets.py` + Gradle | PR, `main`, тег `v*` |

На тег `v*` оба артефакта прикладываются к GitHub Release. Локальные сборки
описаны в соответствующих разделах выше и в `android/README.md`.

## Публикация

`.github/workflows/pages.yml` — на каждый пуш в `main` выкладывает корень
репозитория на GitHub Pages. Отдельной сборки нет: на сайт попадает то, что
лежит в ветке.

## Пуш и защита веток

`main` защищён: работать только через ветку и pull request. Четыре слоя,
которые это обеспечивают.

**1. Учётные данные не лежат в файлах проекта.** Один раз войдите через
Git Credential Manager — он сохранит токен в Windows Credential Manager,
откуда его нельзя случайно закоммитить:

```powershell
cd D:\AI\workspace\TMK-plant
git push -u origin <ветка>     # GCM один раз откроет вход через браузер
```

Если заводите personal access token вручную — **fine-grained**, доступ
только к `redist1984/TMK-plant`, права `Contents: Read and write` **и**
`Workflows: Read and write` (без второго не пройдёт пуш изменений в
`.github/workflows/`), срок 30–90 дней. Отзывается одной кнопкой.

**2. Ruleset на `main`** — файл уже лежит в репозитории, применяется
импортом (GitHub не подхватывает `.github/rulesets/` автоматически):

Settings → Rules → Rulesets → **Import a ruleset** →
`.github/rulesets/main-protection.json`

Что он даёт: прямой пуш в `main` отклоняется сервером, нужен pull request,
ветку нельзя удалить и нельзя форс-пушить. Число обязательных ревью — `0`,
потому что одобрить собственный PR GitHub не даёт: с `1` вы бы не смогли
смёржить свою же ветку.

После первого зелёного PR можно импортировать более строгий
`.github/rulesets/main-protection-strict.json` — он дополнительно требует
пройденной проверки `checks`. Второй файл не импортируйте сразу: если имя
статус-проверки вдруг окажется другим, мерж заблокируется насовсем.
`node tools/ci-check.js` проверяет оба файла (валидный JSON, непустой
`include`, известные типы правил, непустой список проверок).

**3. Локальные хуки** — раннее предупреждение, включаются в каждом клоне:

```powershell
git config core.hooksPath .githooks
```

`.githooks/pre-commit` гоняет `node tools/ci-check.js`;
`.githooks/pre-push` делает то же плюс отказывает в пуше в `main` и требует
имя ветки по соглашению. Это предохранитель, а не граница безопасности:
обходится флагом `--no-verify`.

> В песочнице DSH хуки запускать нельзя — msys `sh` не может создать
> служебный pipe. Поэтому агент работает с `core.hooksPath` снятым, а
> включать его стоит в своём терминале.

**4. CI** — `.github/workflows/checks.yml` на каждый pull request. Главный
слой: он единственный проверяет то, что уже лежит на сервере.

## Известные ограничения

- `tools/check-*.js`, `tools/query-*.js` — геометрические проверки 3D-модели.
  Написаны под окружение с Playwright (`/opt/node-tools/...`, `/opt/pw-browsers`)
  и страницу `model_test.html`, которой в репозитории нет, поэтому в текущем
  виде не запускаются. Требуют портирования.
- `model.html` — один файл ~1 МБ: движок, геометрия и данные вместе. Любая
  правка модели идёт в этот файл.
