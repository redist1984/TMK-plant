# Завод TMK — офлайн-справочник сернокислотного завода

Браузерное приложение (PWA), которое собирает в одно целое 3D-модель завода,
технологическую схему, PFD, блокировки, анализы, перечень КИП и проектную
документацию. Работает без интернета — на планшете или ноутбуке в цеху.

**Живая версия:** https://redist1984.github.io/TMK-plant/

Объект — сернокислотный завод ООО «TMK Chemicals», 500 000 т/год, проект 3147.
Интерфейс двуязычный (RU / UZ), тема светлая/тёмная/системная.

| Вкладка | Файл | Что внутри |

| Схема потоков | `flow.html` | потоки с параметрами, переходы в 3D и PFD |
| PFD | `pfd.html` + `pfd/` | 3 листа, 78 потоков с теплофизикой, 30 карточек оборудования |
| Блокировки | `interlocks.html` | 42 блокировки по 10 листам логических схем |
| Анализы | `analyses.html` | 25 точек аналитического контроля по регламенту п. 9.3 |
| КИП | `kip.html` | 384 прибора |
| Документы | `docs.html` | 151 PDF (планы, паспорта, ГА, ППР) |
| Мнемосхемы | `mnemo.html` + `mnemo/` | 12 экранов АСУТП со значениями из модели: полный экран, 1/2/4 панели |
| Двойник | `twin.html` + `twin/` | стационарная модель линии серы: управления, баланс, блокировки |
| Настройки | `settings.html` | язык, тема, производительность |
| Помощь | `help.html` | справка по приложению |

## Структура

```
index.html            оболочка: шапка, вкладки, iframe-ы, шина postMessage
model.html            ровно одна страница на вкладку; данные зашиты внутрь
flow.html
pfd.html              + pfd/pfd-data.js, pfd/symbols.js, pfd/scan/*.jpg
interlocks.html       + interlocks-data.js, ilk-card.js
analyses.html         + analyses-data.js, anl-card.js
kip.html              + kip-data.js
docs.html             индекс PDF: путь -> заголовок (RU/UZ)
mnemo.html            вкладка «Мнемосхемы»: экраны АСУТП + чипы расчётных значений
mnemo/                screens.json (экраны, горячие точки, показатели) + 12 JPEG
twin.html             вкладка «Двойник»: управления, показатели, блокировки
twin/                 модель: balance.json, model.js, heat.js, temps.js,
                      interlocks.data.js, logic.js, apply.js, state.js,
                      heatcap.js + selftest-ы (см. twin/README.md)
analyses-data.js      данные: приборы, анализы и т. п.
interlocks-data.js
kip-data.js
eq-uz.js              переводы описаний оборудования на узбекский
lang.js  theme.js     язык и тема; родитель рассылает их в iframe-ы
service-worker.js     precache + network-first (кэш только для офлайна)
manifest.json         PWA
vendor/               three.js и OrbitControls (локально, без CDN)
sec_img/              фото и сканы чертежей (178 файлов)
docs_pdf/             проектная документация (151 PDF)
tools/                чекеры, сборка офлайн-версии, проверки геометрии
```

Модули `twin/*.js` работают и в Node (проверки), и в браузере (тег `<script>`).
Классические скрипты делят одну глобальную область, поэтому такие файлы обязаны
быть обёрнуты в IIFE — это проверяется в `ci-check` (проверка `scope`), подробности
в [twin/README.md](twin/README.md).

Страницы — не модули, а самостоятельные документы: каждая грузится в свой
`iframe`, а оболочка `index.html` передаёт между ними сообщения
(`__tmkLangChange`, `__tmkThemeChange`, `__tmkGoto`, `__tmkFullscreen`).
Поэтому `model.html` и `flow.html` тяжёлые — в них зашиты и геометрия, и данные.

## Локальный запуск

Любой статический сервер из корня проекта (через `file://` не работает —
не зарегистрируется service worker):

```powershell
python -m http.server 8765
# затем http://localhost:8765/
```

## Проверки

Всё, что можно проверить без человека, проверяется командами:

```powershell
npm run check           # целостность проекта, без зависимостей (в т.ч. README)
npm run twin            # модель двойника против проектного баланса
npm run twin:ilk        # логика блокировок: 2oo3, латчи, BYPASS
npm run twin:heat       # пар и питательная вода против листа 2
npm run twin:temps      # температуры газа против проекта
npm run smoke           # приложение в браузере: 10 вкладок, данные, поиск
```

`npm run check` (он же `node tools/ci-check.js`) проверяет:

- синтаксис всех `.js` и inline-скриптов;
- **область видимости** скриптов: одно имя на верхнем уровне в двух подключаемых
  файлах и модуль без IIFE, подключённый тегом `<script src>` — эта ошибка роняет
  страницу, но не видна ни в Node, ни линтеру по одному файлу;
- наличие каждого файла из `ASSETS` в `service-worker.js` и полноту precache;
- соответствие `docs.html` ↔ `docs_pdf/`, все `src`/`href` во всех HTML,
  ссылки галерей `IMGS` на `sec_img/`;
- валидность ruleset-файлов, отсутствие ключей и следов Google Drive;
- наличие Android-проекта;
- README не расходится с реальностью: каждая упомянутая команда `npm run` есть
  в `package.json`, каждый путь `node tools/...` существует.

`npm run smoke` открывает приложение в Chrome: одиннадцать вкладок, отсутствие ошибок
JS, число блокировок, анализов, приборов, ссылок на PDF, работу поиска по модели.
Отдельный прогон `npm run smoke:offline` проверяет собранный одиночный файл.

Те же проверки гоняются в CI на каждый pull request: `checks.yml` (целостность и
все три selftest-а двойника) и `smoke.yml` (приложение и офлайн-сборка).
`smoke` — обязательная проверка в ruleset, без неё PR не смержить.

**При изменении любого файла, перечисленного в `ASSETS`, поднимите версию
`CACHE` в `service-worker.js`** (сейчас `tmk-plant-v147`): стратегия
network-first, но старый кэш иначе останется у тех, кто уже открывал приложение.

## Офлайн-сборка одним файлом

Нужен только **Node** — Python не требуется:

```powershell
npm install                       # один раз: sharp для пережатия картинок
npm run offline                   # dist-offline/TMK-plant-offline.html (~40 МБ)
npm run offline -- --with-pdf     # + все PDF внутри (~260 МБ)
```

Имя файла задаётся ключом `--name` (полное, с `.html`):
`npm run offline -- --name TMK-plant-offline-lite.html`.

Без `npm install` сборка тоже работает: `node tools/build-offline.js` просто
не пережимает JPEG, и файл выходит примерно на 11 МБ больше.

Скрипт вкладывает страницы в `index.html` как `srcdoc`-iframe, встраивает
скрипты и шрифты, картинки кладёт base64-блоками и отдаёт blob-URL по
требованию, service worker и manifest убирает. Страницы декодируются лениво —
при открытии собирается только видимая вкладка, остальные при первом
переключении. Результат открывается прямо с диска по `file://`, без сети.

## Android-приложение

`android/` — проект Android Studio: WebView-обёртка вокруг того же сайта.
Подробности в [android/README.md](android/README.md).

Главное: **контент в Android-проекте не хранится**. Каталог
`android/app/src/main/assets/www/` собирается из корня репозитория скриптом
`tools/build-android-assets.js` при каждой сборке APK и добавлен в
`android/.gitignore`. Поэтому правка любого файла в корне автоматически
попадает и в APK — второй копии, которая могла бы разъехаться с сайтом,
просто нет.

Приложение работает полностью офлайн: разрешение `INTERNET` не запрашивается,
внутри APK лежат все страницы, фото и PDF.

## Как это собирается

Три формы проекта собираются из одних и тех же файлов в корне:

| Что | Чем | Когда |
|---|---|---|
| Сайт | `pages.yml` — деплой корня на Pages | пуш в `main` |
| Офлайн-файл | `dist.yml`, job `offline` — `tools/build-offline.js` | PR, `main`, тег `v*` |
| APK | `dist.yml`, job `apk` — `tools/build-android-assets.js` + Gradle | PR, `main`, тег `v*` |
| Целостность | `checks.yml` — `ci-check` и три selftest-а двойника | каждый PR, пуш в `main` |
| Дымовой тест | `smoke.yml` — приложение и офлайн-сборка в Chrome | каждый PR, пуш в `main` |
| Геометрия | `geometry.yml` — проверки модели против базовой линии | когда меняются модель или проверки |

На тег `v*` оба артефакта прикладываются к GitHub Release. Локальные сборки
описаны в соответствующих разделах выше и в `android/README.md`.

Единственное исключение — генератор PFD (`tools/pfd/build.py`): он на Python
(pymupdf, opencv, scikit-image), потому что работает с растром исходного
чертежа. Нужен редко — только когда меняется сам PFD.

## Публикация

`.github/workflows/pages.yml` — на каждый пуш в `main` выкладывает корень
репозитория на GitHub Pages. Отдельной сборки нет: на сайт попадает то, что
лежит в ветке.

## Пуш и защита веток

`main` защищён: работать только через ветку и pull request. Четыре слоя,
которые это обеспечивают.

**1. Учётные данные не лежат в файлах проекта.** Один раз войдите через
Git Credential Manager — он сохранит токен в Windows Credential Manager,
откуда его нельзя случайно закоммитить:

```powershell
cd D:\AI\workspace\TMK-plant
git push -u origin <ветка>     # GCM один раз откроет вход через браузер
```

Если заводите personal access token вручную — **fine-grained**, доступ
только к `redist1984/TMK-plant`, права `Contents: Read and write` **и**
`Workflows: Read and write` (без второго не пройдёт пуш изменений в
`.github/workflows/`), срок 30–90 дней. Отзывается одной кнопкой.

**2. Ruleset на `main`** — файл уже лежит в репозитории, применяется
импортом (GitHub не подхватывает `.github/rulesets/` автоматически):

Settings → Rules → Rulesets → **Import a ruleset** →
`.github/rulesets/main-protection.json`

Что он даёт: прямой пуш в `main` отклоняется сервером, нужен pull request,
ветку нельзя удалить и нельзя форс-пушить. Число обязательных ревью — `0`,
потому что одобрить собственный PR GitHub не даёт: с `1` вы бы не смогли
смёржить свою же ветку.

После первого зелёного PR можно импортировать более строгий
`.github/rulesets/main-protection-strict.json` — он дополнительно требует
пройденных проверок `checks` и `smoke`. Второй файл не импортируйте сразу: если
имя статус-проверки вдруг окажется другим, мерж заблокируется насовсем.
`node tools/ci-check.js` проверяет оба файла (валидный JSON, непустой
`include`, известные типы правил, непустой список проверок).

**3. Локальные хуки** — раннее предупреждение, включаются в каждом клоне:

```powershell
git config core.hooksPath .githooks
```

`.githooks/pre-commit` гоняет `node tools/ci-check.js`;
`.githooks/pre-push` делает то же плюс отказывает в пуше в `main` и требует
имя ветки по соглашению. Это предохранитель, а не граница безопасности:
обходится флагом `--no-verify`.

> В песочнице DSH хуки запускать нельзя — msys `sh` не может создать
> служебный pipe. Поэтому агент работает с `core.hooksPath` снятым, а
> включать его стоит в своём терминале.

**4. CI** — `.github/workflows/checks.yml` на каждый pull request. Главный
слой: он единственный проверяет то, что уже лежит на сервере.

## Генератор PFD

`pfd/pfd-data.js` (78 потоков, карточки, координаты аппаратов и труб) не
правится руками — он собирается из исходного чертежа:

```powershell
pip install -r tools/pfd/requirements.txt
python tools/pfd/build.py docs_pdf/PFD-WZ-POT-262.pdf
```

Разметка (зоны аппаратов, направления потоков, пунктиры, подписи) лежит в
`tools/pfd/eqboxes.py` и `tools/pfd/manual.py` — правится там, а не в
результате.

Внешние программы не нужны: картинки из PDF достаёт PyMuPDF. Раньше
требовался poppler (`pdfimages`), из-за чего генератор не запускался.

Проверено: на текущих версиях зависимостей (см. `requirements.txt`) выход
совпадает с закоммиченными `pfd/pfd-data.js` и `pfd/scan/*.jpg` **байт в
байт** — то есть данные воспроизводимы, а не «однажды сгенерированы».

## Проверки геометрии модели

Отдельный набор проверок того, что 3D-модель сходится физически: трубы не
проходят сквозь аппараты, аппараты не висят в воздухе, ничего не протыкает
стены и крыши, приборы КИП не влезают в чужое оборудование.

```powershell
npm install
npm run geometry            # ~6 минут, нужен установленный Chrome
```

Число находок сравнивается с `tools/geometry/baseline.json`: стало больше —
проверка падает. Подробности в [tools/geometry/README.md](tools/geometry/README.md),
в CI — `.github/workflows/geometry.yml` (запускается, когда меняются модель или
сами проверки).

`tools/check-flow-labels.js` — отдельная проверка подписей на схеме потоков,
работает без браузера: `node tools/check-flow-labels.js`.

## Двойник: стационарная модель линии серы

Вкладка «Двойник» — расчёт участка «сера → сжигание → конверсия → абсорбция».
Не «подогнанные» числа, а стехиометрия и теплофизика, сверенные с проектом:

| Блок | Что считается | Сходимость |
|---|---|---|
| Материальный баланс | S, воздух, SO₂/SO₃/O₂/N₂, кислота, выброс | 0,1 % от проектного баланса |
| Тепло и пар | тепло реакций, пар 6,4 МПа / 450 °C | 85,13 т/ч против 85,1 |
| Температуры газа | печь и ступени из тепла конверсии | печь 1 096 °C против 1 080 (+1,5 %) |
| Блокировки | 42 записи: условия, связки, латчи, BYPASS | связаны с расчётом |

Исходные данные — проектный материальный баланс (3 листа, таблицы потоков) и
текст проектного обоснования. Подробности, формулы и ограничения —
в [twin/README.md](twin/README.md).

Честные ограничения:

- **4-я ступень конвертера** в проектном балансе не сходится сама с собой
  (рост 311 → 415 °C теплом конверсии не объясняется) — точка помечена
  в интерфейсе, а не подогнана;
- **мощность турбины** — оценка по допущению КПД, в балансе её нет;
- **40 блокировок из 42** показывают «без сигнала»: модель не знает уровней
  в баках, давлений пара и температур масла;
- модель **стационарная**: «было — стало», без переходных процессов.

## Известные ограничения

- `tools/query-*.js` (bbox / region / flow) остались от старого окружения с
  `/opt/...` путями и пока не портированы на `tools/geometry`.
- `model.html` — один файл ~1 МБ: движок, геометрия и данные вместе. Любая
  правка модели идёт в этот файл.
- **APK на живом устройстве не проверяется автоматически**: CI собирает APK, но
  установку и работу на планшете проверяет человек.
